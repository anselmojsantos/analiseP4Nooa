Este texto descreve, em ordem cronológica, toda a análise exploratória
feita sobre as estações do CEMADEN em São Paulo: desde a coleta e
limpeza dos dados, passando pela classificação por zona, até a
classificação de status (ativa / inativa) e os agrupamentos finais.


---------------------------------------------------------------------
1. A FONTE DOS DADOS
---------------------------------------------------------------------
O dado inicial não vem de arquivos locais, e sim de um banco de dados
PostgreSQL hospedado na nuvem (Render), criado para o projeto. A
conexão foi feita com a biblioteca SQLAlchemy e a tabela
cemaden_station foi carregada inteira para um DataFrame:

    df = pd.read_sql("SELECT * FROM cemaden_station", engine)

O primeiro passo foi entender o que havia na tabela: 23 colunas com
dados de cadastro das estações (nome, município, sensores, latitude,
longitude, cotas, datas de instalação, etc.). No total, 710 estações
espalhadas por todo o Brasil.


---------------------------------------------------------------------
2. FILTRAR SÃO PAULO
---------------------------------------------------------------------
A tabela traz estações de todo o Brasil. Como o estudo é sobre a
capital paulista, foi aplicado o filtro pelo código IBGE do
município de São Paulo (3550308):

    df_sp = df[df["ibge_code"] == 3550308]

Resultado: 79 estações do CEMADEN dentro de São Paulo capital.


---------------------------------------------------------------------
3. O QUE REMOVER E POR QUÊ (ANÁLISE DOS VALORES VAZIOS)
---------------------------------------------------------------------
Antes de cruzar com as zonas, foi verificada a quantidade de valores
vazios (NaN) com df_sp.isna().sum(). A análise mostrou:

  - cota_alerta, cota_atencao, cota_transbordamento (cotas de
    transbordamento): 79 NaN (100%). Essas cotas só existem para
    estações fluviométricas (que medem nível de rio) e não foram
    cadastradas. Como as 79 estações de SP são todas pluviométricas
    (medem chuva), essas colunas ficam vazias.
  - raw_payload (payload bruto de transmissão): dado técnico pesado
    e sem utilidade para localização.

Como o objetivo desta primeira etapa é apenas a LOCALIZAÇÃO das
estações, essas colunas foram removidas para deixar o DataFrame
enxuto:

    new_df = df_sp.drop(columns=["cota_alerta", "cota_atencao",
                                 "cota_transbordamento", "raw_payload"]
                               ).reset_index(drop=True)


---------------------------------------------------------------------
4. DE ONDE VIERAM AS ZONAS (O GEOJSON)
---------------------------------------------------------------------
Para saber em qual região cada estação está, era preciso saber o que
é cada região "no mapa", ou seja, o polígono de cada zona.

A zona foi baixada de uma fonte pública e oficial da Prefeitura de
São Paulo: o dataset "Subprefeituras" do portal de Dados Abertos
(URBS), que traz os polígonos das 32 SUBPREFEITURAS do município.

  FONTE (download): Prefeitura de SP - Dados Abertos (URBS),
  dataset "Subprefeituras do Município de São Paulo":
  - Página do recurso:
    https://dadosabertos.urbis.prefeitura.sp.gov.br/tl/dataset/subprefeituras/resource/0e38226b-f623-444f-8069-9dd6c8a2a0af
  - Download direto (arquivo subprefeituras.geojson):
    https://dadosabertos.urbis.prefeitura.sp.gov.br/dataset/7310f0b8-ab0a-4e61-9568-604263457e39/resource/0e38226b-f623-444f-8069-9dd6c8a2a0af/download/subprefeituras.geojson

Ficha técnica do arquivo baixado (subprefeituras.geojson):
  - formato GeoJSON, 32 subprefeituras (campos id, nome, sigla);
  - projeção EPSG:31983 (metros) - SIRGAS 2000 / UTM zona 23S;
  - cobertura: Município de São Paulo.

OBSERVAÇÃO: o GeoSampa (https://geosampa.prefeitura.sp.gov.br/) é o
portal que publica e mostra essa camada no mapa, mas a página de
metadados dele não tem botão de download. O download do arquivo foi
feito pelo portal de Dados Abertos (URBS), no link acima.

Cada subprefeitura foi associada a uma das 5 zonas da cidade e, com o
geopandas, os polígonos foram unidos (dissolve) em apenas 5, um por
zona:

    Centro, Norte, Sul, Leste, Oeste

O resultado foi salvo em zonas_sp.geojson.

OBSERVAÇÃO SOBRE O GEOJSON: existe ainda um arquivo alternativo
(subprefeituras.json, convertido da camada KML do GeoSampa) com
propriedades complexas (dicionários "{}", sp_codigo, sp_nome,
sp_areakmt etc.). Para a análise foi usado o arquivo oficial
subprefeituras.geojson (Dados Abertos URBS), que já vem limpo com os
campos id, nome e sigla. O arquivo final, zonas_sp.geojson, foi
simplificado para conter apenas a coluna "zona" e a geometria.


---------------------------------------------------------------------
5. O CRUZAMENTO COM O GEOPANDAS
---------------------------------------------------------------------
A ideia central: cada estação tem uma coordenada (lat/lon) e cada
zona tem um polígono. O geopandas testa, para cada estação, se o
ponto está DENTRO do polígono de uma zona (teste Point-in-Polygon).

    zonas = gpd.read_file(r"C:\TI\Projetos Univesp\Projeto - 4\zonas_sp.geojson")

    gdf = gpd.GeoDataFrame(
        new_df,
        geometry=gpd.points_from_xy(new_df["longitude"], new_df["latitude"]),
        crs="EPSG:4326",
    )
    gdf = gpd.sjoin(gdf, zonas, how="left", predicate="within")
    gdf["zona"] = gdf["zona"].fillna("Fora de SP")
    new_df = gdf.drop(columns=["geometry", "index_right"]).copy()

Como nem toda estação cai dentro de algum polígono (ex.: imprecisão
de coordenada), o valor vazio foi convertido em "Fora de SP".


---------------------------------------------------------------------
6. AJUSTE FINAL (CASO CIDADE TIRADENTES 2)
---------------------------------------------------------------------
A estação "Cidade Tiradentes 2" foi marcada como "Fora de SP" mesmo
estando na Zona Leste: suas coordenadas estavam ~37 m além do limite
oficial. Para absorver essa imprecisão, os polígonos ganharam uma
tolerância (buffer de 100 m) antes do cruzamento:

    zonas["geometry"] = zonas.to_crs("EPSG:31983").geometry.buffer(100).to_crs("EPSG:4326").geometry

Com isso a estação passou a ser classificada corretamente como Leste.

---------------------------------------------------------------------
8. ENTENDIMENTO DAS COLUNAS DE DATA
---------------------------------------------------------------------
O DataFrame tem 4 colunas de data, todas com hora embutida:

  - installation_date (data de instalação)
  - registration_date (data de registro no sistema)
  - last_transmission (última transmissão de dados)
  - inactive_since (quando foi marcada como inativa)

Uma descoberta importante desta análise: a coluna inactive_since
NÃO significa "desativada permanentemente". Ela registra a última
falha de comunicação da estação. Muitas estações transmitiram
DEPOIS da data registrada em inactive_since, ou seja, voltaram a
operar.

Verificação feita:

    df_cemaden_station["transmitiu_apos_inativacao"] = (
        df_cemaden_station["last_transmission"]
        > df_cemaden_station["inactive_since"]
    )

Resultado: 51 estações transmitiram depois de inactive_since
(reativadas), e 28 não transmitiram (inativas de verdade).


---------------------------------------------------------------------
9. CLASSIFICAÇÃO DE STATUS (REATIVADA / INATIVA)
---------------------------------------------------------------------
A partir dessa descoberta, criamos uma coluna "status" para cada
estação:

    df_cemaden_station["status"] = df_cemaden_station.apply(
        lambda r: "reativada"
        if r["last_transmission"] > r["inactive_since"]
        else "inativa",
        axis=1,
    )

Interpretação:
  - "reativada" → a estação teve falha, foi marcada como inativa,
    mas voltou a transmitir.
  - "inativa"   → a estação teve falha e NÃO voltou mais.

Total:
  - 51 estações reativadas
  - 28 estações inativas


---------------------------------------------------------------------
10. AGRUPAMENTO POR ZONA
---------------------------------------------------------------------
Com o status definido, agrupamos as estações por zona para ver
quantas reativaram e quantas ficaram inativas em cada região:

    group_zona = (
        df_cemaden_station
        .groupby("zona")
        .agg(
            qtd_estacoes=("id_estacao", "count"),
            reativadas=("status", lambda x: (x == "reativada").sum()),
            inativas=("status", lambda x: (x == "inativa").sum()),
        )
        .sort_values("qtd_estacoes", ascending=False)
    )

    group_zona["pct_reativada"] = (
        group_zona["reativadas"] / group_zona["qtd_estacoes"] * 100
    ).round(1)

    group_zona["pct_inativa"] = (
        group_zona["inativas"] / group_zona["qtd_estacoes"] * 100
    ).round(1)

O resultado mostra, por zona:
  - quantidade total de estações
  - quantas reativaram
  - quantas ficaram inativas
  - percentual de cada caso

Isso ajuda a identificar quais zonas têm rede mais resiliente
(aquelas com alto percentual de reativadas) e quais têm mais
estações abandonadas.


---------------------------------------------------------------------
11. OUTRAS ANÁLISES POSSÍVEIS
---------------------------------------------------------------------
Além do agrupamento por zona, foi possível calcular:

  - dias_entre_inativacao_e_transmissao: quantos dias se passaram
    entre a inativação e a volta da transmissão (só faz sentido para
    estações reativadas).

    df_cemaden_station["dias_entre_inativacao_e_transmissao"] = (
        df_cemaden_station["last_transmission"]
        - df_cemaden_station["inactive_since"]
    ).dt.days

    Valores:
      - Positivo → reativada (voltou depois da falha)
      - Zero → voltou no mesmo dia
      - Negativo → inativa (não voltou)

  - Distribuição por zona e por status (crosstab).
  - Distribuição por ano de inativação.
  - Mapa interativo com cores por status (reativada = verde,
    inativa = vermelho).
